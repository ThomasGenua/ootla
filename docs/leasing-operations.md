# Leasing operations release

This release extends Ootla's existing CRM with eight connected feature areas. All work is stored in PostgreSQL and respects organization, staff role and related-property access.

| Workspace | Workflow |
| --- | --- |
| Inquiry forms | An administrator publishes a form for one property, optionally chooses an owner and approved embedding origins, and shares its link. Submissions create separate contacts/leads and inbox messages. Campaigns and potential duplicates are recorded. |
| Shared inbox | Staff see unread inquiries, own or close conversations, use templates, edit drafts and explicitly review a send. Email and SMS have separate recorded contact preferences. Unmatched or ambiguous incoming messages require administrator review. |
| Follow-up rules | Administrators configure unanswered inquiries, approaching tours and incomplete applications. Each occurrence creates a task and optional unsent draft once. Responses, cancelled/completed tours, submitted applications, closed leads and disabled rules stop relevant work. |
| Resident requests | An active resident uses their existing applicant account to submit a maintenance request, attach evidence and follow updates. Staff assign ownership and post resident-visible status updates. |
| Search & saved work | Search accessible leads, contacts, properties, applications and tasks; save personal lead filters; select leads for an atomic bulk assignment; search activity records. |
| Property knowledge | Administrators publish sourced property references. The assistant can answer a staff question using up to five relevant excerpts, display captured source versions, preserve the original result, save staff edits and collect feedback. |
| Operations reports | First-response times, observed time in stage, tour attendance, property comparisons and inquiry campaigns complement the existing leasing conversion report and CSV export. |
| Interface | New workspaces include empty states and narrow-screen layouts. Feature modules load by route instead of one large initial JavaScript bundle. |

## Install and validate

Run `npm ci`, `npm run db:migrate`, `npm run build`, then restart the application. Migration `018_leasing_operations.sql` is additive; existing identities are preserved. Readiness requires this migration. Back up the database before a production migration using the existing release guide.

Use `npm run check:operations` and `npm run check:operations-browser` with the documented local PostgreSQL test cluster. Both own disposable databases, test the lease-to-resident prerequisites and clean up only their own fixtures. They never send provider messages. `npm run check:release` retains the prior screening, payments, lease, assistant/team and backup/restore checks. CI runs both new suites alongside the existing release/browser/container checks.

## Delivery configuration

Live delivery is off by default. The isolated demo always simulates sends. Set `COMMUNICATIONS_ENABLED=true` only in a non-demo environment with an HTTPS `APP_URL`, and set `COMMUNICATIONS_ORGANIZATION_ID` to the intended live organization. Email and SMS can be configured independently. Credentials stay in server environment variables and are never returned to the interface.

For Resend, set `RESEND_API_KEY`, a verified `RESEND_FROM_EMAIL`, the inbound `RESEND_REPLY_DOMAIN` hostname, and `RESEND_WEBHOOK_SECRET`. Configure a signed webhook at `APP_URL/api/communications/resend` for `email.received`, `email.sent`, `email.delivered`, `email.bounced`, `email.failed` and `email.complained`. Configure inbound DNS for the reply domain according to Resend's instructions. Replies use an HMAC-protected conversation address. Incoming message bodies are retrieved with the Resend receiving endpoint; attachments and HTML are not imported.

For Twilio, set `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN` and a messaging-capable E.164 `TWILIO_FROM_NUMBER`. Configure incoming messages at `APP_URL/api/communications/twilio/incoming` using POST. Ootla supplies a per-message status callback when creating each SMS. Signature validation uses the exact public `APP_URL` and request path; redirects or an incorrectly configured origin will fail verification. STOP and equivalent opt-out keywords suppress SMS for every matching contact in the organization, including ambiguous duplicate contacts. Opt-ins require staff evidence; an inbound START does not automatically opt the contact back in.

Provider documentation: [Resend send email](https://resend.com/docs/api-reference/emails/send-email), [verify Resend webhooks](https://resend.com/docs/webhooks/verify-webhooks-requests), [retrieve received email](https://resend.com/docs/api-reference/emails/retrieve-received-email), [Twilio Message resource](https://www.twilio.com/docs/messaging/api/message-resource), [Twilio request validation](https://www.twilio.com/docs/usage/security#validating-requests).

Production credential verification and a provider-approved live test remain deployment work. Mocked transport and signed callback tests establish application behavior; they do not establish sender/domain registration or live deliverability.

## Behavior and operating limits

- A saved draft does not send anything. A staff-reviewed send checks current permissions, every related property, the recipient, channel permission and provider configuration. Demo sends are labeled simulated. Accepted means the provider accepted the request; delivered requires its callback. Failed and uncertain messages are not automatically retried. Check the provider before creating another draft after an uncertain outcome. A process interrupted during submission becomes uncertain when reopened after two minutes.
- Send requests are durable and serialized, with a 100-send organization hourly cap. Resend receives an idempotency key. Incoming callbacks are signed and replay-protected. Delivery callbacks that arrive before the HTTP send response are retained. Twilio terminal outcomes never regress; Resend updates use provider event timestamps. Unmatched messages are retained for review, without creating or merging identities.
- Inquiry forms use signed, expiring challenges, a short dwell requirement, a honeypot, HMAC rate buckets and duplicate request handling. These reduce basic abuse; they do not verify a visitor's identity. Identical content within 15 minutes returns the same receipt. Limits are 20 submissions per observed IP and 200 per form per 15 minutes. The app does not trust forwarded IP headers; configure an appropriate verified edge policy before high-volume public use.
- Only explicitly allowed origins can embed a published form. Other application pages retain framing protection. Public form responses contain only a receipt, never customer identities or CRM IDs.
- Follow-up processing runs every minute, with non-overlapping local ticks and database locks across instances. Batches rotate through up to 100 rules, 100 new occurrences per rule and 500 existing runs per rule. Large backlogs take additional ticks. Stop conditions cancel open tasks and untouched automation drafts. Staff-edited drafts remain available for review. Automation never invokes a messaging provider. A tour or application produces one occurrence per rule; rescheduling the same tour does not create a second reminder.
- Resident access requires the same active application participant/contact as an active resident relationship. It does not grant household-wide access. The portal shows the latest 100 requests and 100 updates per request; uploads are limited to ten PDF, PNG, JPEG or text files, each up to 2 MB. The daily submission limit is ten per account. This is a service-request portal, not an emergency dispatch channel.
- Saved lead views belong to their staff author, with up to 50 per account. Bulk assignments are limited to 100 selected leads and fail together if any version or access check fails. They do not silently change conversation ownership. Search results and activity are paginated; property selectors include search and paging.
- Published knowledge is deliberately curated by administrators. Only up to five 1,600-character excerpts, the staff question and limited record facts enter the AI context. Treat questions/references as data, not instructions. Stored source snapshots identify what was used at generation time; later edits or withdrawal do not rewrite historical drafts. The demo returns a clearly labeled excerpt-based answer and makes no AI call. Staff edits clear the reviewed marker and preserve the original model output.
- Reports use leasing leads created in the chosen period and outcomes recorded through now. First response includes accepted or delivered provider messages and labeled simulations. Attendance excludes scheduled and cancelled tours. Stage durations start when this migration observes an existing stage; earlier history is unknown. Property/campaign comparisons show up to 100 groups. These are descriptive operational counts, not provider revenue or payment reports.

Disabling communications blocks new sends and webhook processing; preserve provider events for later reconciliation. Disabling a rule stops its pending work on the next pass. Unpublishing a form blocks new submissions; unpublishing knowledge removes it from future answer context. Existing records and history are retained.
